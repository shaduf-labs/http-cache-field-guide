HTTP Cache Field Guide

Choose cache headers that fit the response—and diagnose “old content” without accidentally sharing private data.

Decision order: who may store it → how long it may be fresh → how it should validate → which request variants must stay apart.

The short answer

Separate storage audience, freshness, stale permission, and matching. Use private, no-cache when a personalized response may stay in a browser but must not enter a shared cache; use no-store when compliant HTTP caches should not intentionally retain it. Add validators for cheap revalidation. When both conditional validators are sent, If-None-Match wins. A stale extension never grants storage or repairs a bad key. Request Cache-Control fields are different: they express advisory client preferences, not response policy or universal origin/purge commands.

New dated follow-up · 7 Oct 2026 · request directives

A request can express a cache preference; it cannot command every cache

RFC 9111 calls request directives advisory: caches may honor them, but need not. Response directives have a different, mandatory role. Request no-cache is not guaranteed origin revalidation, max-age=0 is not a purge, and no-store does not delete an older entry. only-if-cached is a stored-response preference—not a universal no-forwarding guarantee.

New dated follow-up · 4 Oct 2026 · browser HTTP cache

Same resource URL, separate browser contexts

Browser HTTP-cache partitioning can make the same URL a separate local candidate under a different top-level site. It does not replace HTTP matching, Vary, freshness, or validation, and it does not configure a CDN or proxy. Use response policy—not partitioning—to control private or sensitive storage.

New dated follow-up · 1 Oct 2026 · HTTP redirects

A moved URL can keep an old redirect target

Each redirect response belongs to the URI requested at that hop. A cached response can retain an older Location; a later redirect in the chain is a separate cache candidate. A new policy does not erase older copies.

New dated follow-up · 25 Sep 2026 · standards-grounded

When stale HTTP content is allowed

Ask four questions in order: was the response stored, which max-age or shared s-maxage applies, does a bounded stale permission apply, and can the entry validate? stale-while-revalidate and stale-if-error are support-dependent permissions. Under the portable RFC 9111 reading, do not treat them as overrides for no-cache, must-revalidate, proxy-revalidate, or shared s-maxage revalidation.

New · 28 Sep 2026 · service-worker update

A worker update does not replace an open page

A successful worker candidate can wait while old clients use the registration. Forced activation can change their controller without replacing their in-memory code. Cache Storage is script-managed and is not cleared by activation; retain old assets until the application compatibility rule allows cleanup.

Four decisions before shipping a cacheable response

DecisionQuestionUseful starting point
1 · AudiencePrivate or safely shared? Cookies and authentication can make the body user-specific.Decide the audience before adding public or s-maxage.
2 · LifetimeHow long is fresh?Set explicit max-age; shared caches may use a separate s-maxage.
3 · ValidationHow does stale content recover?With both validators, If-None-Match is evaluated before If-Modified-Since.
4 · VariantsWhat changes the body?Keep target URI, Vary-nominated fields, cookies, authorization, and unlisted application inputs from creating a privacy mismatch.

New · 16 Sep 2026

Locate the serving layer

An old response may come from history/bfcache, a service worker/Cache API, the browser HTTP cache, an intermediary, or the origin. Start by asking whether a new fetch happened; then seek positive, named evidence rather than inferring from 200, a DevTools label, or a missing header.
