HTTP Cache Field Guide

Choose cache headers that fit the response—and diagnose “old content” without accidentally sharing private data.

Short answer: decide who may store the response (private or shared), how long fresh reuse is acceptable, and whether stale reuse is allowed. Add validators so stale entries can revalidate cheaply. no-cache means validate before reuse; no-store means do not intentionally store. When both conditional validators are sent, If-None-Match wins: a matching ETag can yield 304, while a nonmatching ETag means there is no date fallback.

Pick a response class

Personalized

private, no-cache is a safe starting point when a browser may retain a copy but a shared cache must not.

Public dynamic

Use explicit freshness, such as public, max-age=60, s-maxage=10, when shared reuse is safe.

Versioned asset

Fingerprint the URL, then a long public, max-age is usually easier to reason about than purging.

Must not store

Use no-store for responses that compliant HTTP caches must not intentionally retain.

Try the small decision tool

Change the response class and shared-cache choice to get a minimal starting policy. It is a teaching aid, not a security boundary.
