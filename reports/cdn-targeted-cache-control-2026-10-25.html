CDN-targeted Cache-Control

RFC 9213 defines a cache-specific policy-selection mechanism. Cloudflare documents its own precedence and forwarding for standard and proprietary targeted fields.

Evidence status: documentation-only. RFC Editor pages and Cloudflare documentation were checked 25 Oct 2026, 06:09–06:12 UTC. Cloudflare’s CDN-Cache-Control page identifies its last update as 16 Apr 2026. No endpoint, browser, cache, Cloudflare zone/account, provider, or third-party system was tested. All response headers and ages below are synthetic examples, not observations or deployment instructions.

Finding

RFC 9213’s CDN-Cache-Control is a standardized, CDN-targeted response field. It lets a CDN use one policy while browsers and other caches use ordinary Cache-Control. By contrast, s-maxage is part of ordinary Cache-Control and applies to shared caches generally, not only CDNs. RFC 9213 §3; RFC 9111 §5.2.2.10.

A conforming targeted cache has an ordered list of field names. For each response, it selects the first valid, non-empty field on that list and uses its directives instead of the response’s ordinary Cache-Control and Expires. If no listed field is usable, it falls back to ordinary HTTP cache-control rules. The field name alone does not prove support or identify the cache’s target list. RFC 9213 §2.2.

The freshness model stays end-to-end. A CDN may use a longer targeted lifetime while a downstream browser or ordinary proxy sees the response’s accumulated Age exceed its shorter ordinary lifetime. “Fresh at the CDN” does not mean fresh at every downstream cache. RFC 9213 §2.3.

1. What targeted control adds beyond s-maxage

RFC 9111’s ordinary shared-cache freshness choice is s-maxage, then max-age, then Expires minus Date; a heuristic may apply where allowed if no explicit expiration is available. A private cache ignores s-maxage and normally uses max-age, then Expires, or an allowed heuristic. A response is fresh only when its freshness lifetime is greater than its current age. RFC 9111 §4.2, §5.2.2.1, §5.2.2.10, §5.3.

s-maxage overrides max-age and Expires for each shared cache using ordinary rules. It also imports proxy-revalidate semantics, requiring successful validation before stale reuse, and it can permit shared reuse of a response to a request carrying Authorization under RFC 9111 §3.5. It does not distinguish a CDN from a shared proxy. RFC 9111 §3.5; §5.2.2.10.

RFC 9213 adds a separate targeting mechanism. Its targeted field carries cache directives with a distinct field name for a particular class of cache. RFC 9213 defines CDN-Cache-Control for caches in a distributed network operating on behalf of an origin (a CDN). A targeted cache must implement at least max-age, must-revalidate, no-store, no-cache, and private; it should implement other directives that it supports in ordinary Cache-Control. In either policy, no-store and no-cache make max-age inoperative. RFC 9213 §2.2.

2. Target-list selection and fallback

  1. The cache has an ordered target list. The most applicable field name comes first. The list may be fixed, configured, or generated per request.
  2. The cache selects the first field on that list whose value is valid, non-empty, and parsable. It applies that field’s directives instead of the response’s ordinary Cache-Control and Expires; this is not directive-by-directive merging.
  3. An empty field or a field with a parsing error is ignored. If no listed field is usable, the cache falls back to ordinary HTTP cache-control mechanisms, including the shared-cache s-maxage/max-age/Expires order.
  4. A targeted field not on the cache’s list must not change that cache’s behavior and must be passed through. The -Cache-Control suffix is a field-name convention; it is not proof that the cache recognizes the field.

Targeted values are Structured Field Dictionaries, not ordinary Cache-Control fields with alternate names. RFC 9213 warns that parsing a targeted field with a Cache-Control parser can create interoperability problems. For example, max-age takes an integer; a decimal such as max-age=2.5 is not a valid integer value. RFC 9213 §2.1; RFC 8941.

3. One freshness model and Age

RFC 9111 defines Age as an estimate, in seconds, of time since the response was generated or successfully validated at the origin. It reflects residence in caches along the path plus transit time; it is not a new freshness clock that starts at each hop. A cache compares its selected freshness lifetime with the message’s current age. RFC 9111 §4.2.1, §4.2.3, §5.1.

A cache using CDN-Cache-Control: max-age=600 can consider a response fresh at Age: 300. A downstream browser using Cache-Control: max-age=60 and an ordinary shared proxy using s-maxage=120 can each consider that same response stale. Those caches may need to validate or fetch rather than reuse it without validation. RFC 9213 §2.3 uses Age: 1800, max-age=600, and CDN-Cache-Control: max-age=3600 to make the same distinction.

RFC 9213 mentions possible deployment techniques such as removing Age or updating Date/Expires, but does not require them. Do not assume a provider resets age or rewrites dates unless that named product documents it or an authorized capture establishes it. A targeted lifetime does not erase accumulated age.

5. Cloudflare-specific precedence and forwarding

The following behavior comes from Cloudflare product documentation. It is not a requirement for all RFC 9213 implementations. Cloudflare documents its proprietary field as more specific than the standardized CDN field.

Origin fieldsDocumented Cloudflare cache inputDocumented downstream behavior
CDN-Cache-Control (and possibly Cache-Control)Cloudflare evaluates CDN-Cache-Control; ordinary Cache-Control does not affect the Cloudflare decision when the targeted field is used.Cloudflare proxies the standard field downstream for other CDNs and proxies ordinary Cache-Control as received.
Cloudflare-CDN-Cache-Control (and possibly ordinary Cache-Control)Cloudflare uses its proprietary field as its Cloudflare-specific policy.Cloudflare does not proxy the proprietary field; downstream caches use ordinary Cache-Control/Expires if present, or their normal fallback.
Both targeted fieldsCloudflare-CDN-Cache-Control takes precedence over CDN-Cache-Control.The standard field is forwarded for downstream CDNs; the proprietary field is suppressed.

The specific-field-first behavior is consistent with an RFC 9213-style target list such as [Cloudflare-CDN-Cache-Control, CDN-Cache-Control], but the exact Cloudflare implementation remains a product rule. RFC 9213 says a cache using CDN-Cache-Control typically forwards it and may remove it when undesirable. Cloudflare documents forwarding the standard field and suppressing the proprietary field. RFC 9213 §3.1; Cloudflare CDN-Cache-Control.

Rules that can change the result

  • A Cache Response Rule using set_cache_control takes precedence over origin-set Cloudflare-CDN-Cache-Control and CDN-Cache-Control. Cloudflare says Cache Response Rules take precedence over conflicting Cache Rules. Its example has a response rule’s s-maxage=3600 win over a Cache Rule Edge TTL of 7200 seconds.
  • A Cache Rule’s Edge Cache TTL overrides the targeted header’s edge lifetime. Browser Cache TTL changes only the ordinary Cache-Control response field; it does not modify either targeted field. Cloudflare says Expires does not affect its caching decision when targeted fields are used. If no targeted or ordinary cache-control value is received, Cloudflare directs cacheable assets to its general defaults.
  • Cloudflare’s CDN-Cache-Control page says surrogates do not honor origin Cache-Control when Surrogate-Control is present, even when that field has no directives. The documentation does not establish a complete ordering of Surrogate-Control against both targeted fields; that combination remains a configuration question.
  • Cloudflare’s cache-response documentation gives header precedence as Cloudflare-CDN-Cache-Control > CDN-Cache-Control > Cache-Control. It documents targeted no-store or bare private as possible BYPASS cases. An Edge Cache TTL rule configured to ignore origin controls overrides those directives. Cloudflare describes no-cache, max-age=0, or s-maxage=0 as cache-and-revalidate paths under applicable Origin Cache Control behavior rather than BYPASS. These are Cloudflare behavior statements and remain configuration-dependent.
  • Cloudflare’s Origin Cache Control page adds an Authorization caveat: setting Cloudflare-CDN-Cache-Control turns OCC on regardless of the ordinary OCC toggle. Cloudflare then applies its Authorization logic and documents s-maxage, must-revalidate, or public as permitting cache in that case. Do not treat that product-specific table as a universal rule or as evidence that any response is safe to share.

This targeted-field guide complements the separate Cloudflare Cache Rules and Origin Cache Control guide, which focuses on edge/browser TTL, keys, and purge scope.

6. Privacy eligibility and cache-key boundary

RFC 9213 warns that multiple policies can confuse deployments and cause unintended reuse of sensitive information. A valid targeted field can intentionally tell the target cache to store a response even while ordinary Cache-Control: no-store prevents other caches from storing it. Therefore a generic private or no-store field is not necessarily a veto for a targeted cache that selected a separate valid policy. RFC 9213 §5; §3.1.

private prevents shared storage when it is the selected policy; no-store applies to private and shared caches; and no-cache permits storage but requires successful validation before reuse. RFC 9111 cautions that no-store alone is not a reliable privacy guarantee against malicious or compromised caches. If a CDN must not store a response, include the restrictive directive in the targeted field that it actually selects or omit that targeted field. Do not assume the selected field is merged with ordinary controls. RFC 9111 §5.2.2.4, §5.2.2.5, §5.2.2.8.

Freshness policy is not identity policy. RFC 9111’s minimum cache key includes request method and target URI. Vary can distinguish representations using nominated request fields, and implementations may add other key material. A targeted field does not add Cookie, Authorization, tenant, language, device, query, or any other dimensions to a key. A key that collapses user-, tenant-, or content-negotiation variants can expose or mis-serve data even with a correct TTL. RFC 9111 §2; §4.1.

Cloudflare custom cache-key settings are separate from targeted-field selection and have their own product and plan constraints. This review did not re-audit all selector counts or request-size limits from the earlier Cloudflare guide. Check the exact current account settings and resulting key for an authorized named zone; no key option or Vary policy is assumed here.

7. Limits and unresolved questions

  • No universal support claim. RFC 9213 defines semantics for conforming caches; it does not prove that a specific CDN, browser, proxy, or downstream network implements or enables targeted fields. A target list can vary by request.
  • No zone result. Cloudflare’s docs do not reveal an unprovided zone’s Cache Response Rules, Cache Rules, OCC state, Edge/Browser TTL, key, headers, POP/tier behavior, or response age.
  • Unverified details. Malformed or empty targeted-field handling at a particular Cloudflare configuration, age/date rewriting, additional products, and a concrete downstream topology were not tested. Apply RFC 9213 requirements to conforming implementations, not as a deployment observation.
  • No live probe. No authorized URL or target was supplied, so no browser capture, HTTP request, cache hit, Age, or downstream-staleness observation was attempted. No third-party system test was authorized or run.
  • Example scope. The synthetic matrix illustrates standards and vendor documentation only. It is not a universal configuration recommendation. Review privacy and key isolation before increasing a CDN lifetime for private or credentialed content.
